How to deploy automatically to Hostinger

From a push to GitHub to a verified update on ayah.kamalahmed.me—with the build, SSH access, and secrets in the right places.

The short answerA GitHub push updates the repository. A GitHub Actions workflow must build this Vite project and publish its output to the subdomain’s Hostinger folder. That workflow is now connected to pushes on main.

01

Why a GitHub push did not change the subdomain

The main domain and the Ayah Grammar subdomain have separate deployment paths.

The main domain’s Hostinger connection watches its own repository. The Ayah Grammar repository contains React, TypeScript, source data, and build scripts. Hostinger serves the finished static files from the subdomain’s document root. It cannot show new app code merely because the source changed on GitHub.

The production artifact is the dist/ directory produced by npm run build. It contains the HTML, JavaScript, styles, Quran chapter files, study data, icons, service worker, and hosting rules. There is no server database or running Node process on Hostinger for this app.

One repository push can now start the entire release. The workflow does the build and transfer that previously had to be done by hand.
02

What happens after a push

The workflow file is .github/workflows/deploy-hostinger.yml. It runs when a commit reaches main; it can also be started manually from GitHub Actions.

01 / PUSHGitHub receives the commitOnly the Ayah Grammar main branch triggers this site’s workflow.
02 / BUILDTests and Vite build runGitHub installs dependencies with Node 26 and creates dist/.
03 / VERIFYFiles are staged over SSHSHA-256 checks compare the uploaded files to the local build.
04 / PUBLISHThe entry page switches lastThe new index.html goes live after the other files verify.

The script scripts/deploy-hostinger.sh uses incremental rsync. Old content-hashed assets remain available for readers with a tab open during a release. Release staging is outside the public web directory. The subdomain’s live folder receives only built files, never the source checkout.

What “automatic” means here

A successful push to main starts deployment without a manual upload. If a test, build, SSH connection, or file check fails, the Actions run reports failure. A GitHub commit alone is not a claim that the website updated.

03

The one-time Hostinger connection

This project’s connection has already been configured. These are the pieces to understand or recreate if the hosting account changes.

  1. Confirm the subdomain folder in hPanel.Use Hostinger’s SSH Access information and the document root shown for ayah.kamalahmed.me. The app is served at the subdomain root, so its built index.html belongs there.
  2. Use a dedicated SSH key.Keep its private half outside the checkout. Add only the public half to the Hostinger account’s ~/.ssh/authorized_keys. Verify that this key can log in before adding it to GitHub.
  3. Pin the server’s SSH identity.Check the host-key fingerprint through an existing trusted connection. Save the verified known_hosts entry as an Actions secret. The workflow keeps strict host-key checking enabled.
  4. Save credentials in GitHub Actions settings.Open this repository’s Settings → Secrets and variables → Actions. Add the two secrets and four variables below. Never paste their values into a commit, issue, README, or workflow file.
NameStored asPurpose
HOSTINGER_DEPLOY_KEYSecretDedicated SSH private key
HOSTINGER_KNOWN_HOSTSSecretVerified SSH host-key entry
HOSTINGER_DEPLOY_HOSTVariableHostinger SSH host
HOSTINGER_DEPLOY_USERVariableHostinger SSH user
HOSTINGER_DEPLOY_PORTVariableSSH port
HOSTINGER_DEPLOY_ROOTVariableAbsolute subdomain document root

The table deliberately shows names and purposes, not account values. GitHub documents Actions secrets; Hostinger documents its Git deployment option. This project uses the verified build-and-SSH workflow because the live subdomain needs Vite’s built output.

Keep access private

Do not put the source repository into hPanel’s “Create a New Repository” form for the existing subdomain folder. Do not disable SSH host-key checks. If the key is ever replaced, remove the old public key from Hostinger and replace the matching GitHub secret.

04

How to publish the next change

Review the changes locally, run tests, and commit them. Pushing to main starts the deployment. The same checkout can use the Node version listed in .nvmrc.

npm ci
npm test
npm run build
git status
git add <files-you-intend-to-publish>
git commit -m "Describe the change"
git push origin main

Then open GitHub Actions for Ayah Grammar and choose the newest “Deploy Ayah Grammar to Hostinger” run. A deliberate repeat can be started with Run workflow there or with:

gh workflow run deploy-hostinger.yml -R kamalahmed/ayah-grammar

The production Actions environment can require reviewers. For unattended deployment on every successful push, that environment must not have a required-reviewer gate.

05

Confirm the website actually changed

Look for the final Published and verified <commit> line in the Actions log. Then open ayah.kamalahmed.me in a fresh tab. Check a surah, tap a word to open study, and open the 500-verb library. The live offline manifest lists the public files produced by the build.

  • If the live page looks old, reload it once so the service worker can update. Check the Actions result and live files before assuming a browser cache issue.
  • For mobile offline use, choose Display → Offline reading → Save for offline use while online and wait for completion. The content pack is roughly 45 MB; audio still streams.
  • On an iPhone, save the pack inside the installed Home Screen app if that is where you read. Its storage is separate from Safari’s tab storage; browser storage can also be evicted.
06

If a deployment fails

Start with the failed Actions step. A test or build failure needs a source fix. An SSH failure calls for checking the stored host, port, key, host-key entry, and Hostinger SSH access. A hash-check failure means the staged or live files did not match the build; do not call that release complete.

For rollback, review the earlier verified commit, build it, and run the same deployment script for that commit. The script keeps release directories outside the web root and switches the entry page last. A transfer interrupted after stable data files begin updating may leave those files newer than the old entry page, so inspect the live site after an interrupted release.

07

Node, dependency checks, and the live site

The workflow uses actions/checkout@v7 and actions/setup-node@v7. Their action runtime is separate from the project’s build runtime. The project reads Node major 26 from .nvmrc and requests the newest patch in that major line; the current local compatibility check used Node 26.10.0. Its dependency lockfile and Node type definitions are checked against that line.

Node is needed on the GitHub runner to install packages, test, and build. The finished website is static HTML, JavaScript, styles, and JSON on Hostinger. Changing the workflow’s Node version does not install Node on the Hostinger account.
